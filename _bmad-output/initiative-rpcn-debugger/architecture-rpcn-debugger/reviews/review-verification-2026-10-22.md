## Verdict

Every API name and every as-built claim added on 2026-10-22 holds up against the code and the v4.81 engine source. The weak spot is the Stack table: the `updated: 2026-10-22` stamp covers the AD text only. No `(version)` memlog entry exists after 2026-10-08/09, and on the day of the update the pins are three Connect minors, three benthos minors and four Go patch releases behind. The newest Connect needs Go 1.27. One AD-7 claim ("each stepper mode copies its parent's engine behaviour") is subtly wrong for `try` and `catch`: the execution order differs.

## D. AD-7 reality check: execution order in `try` and `catch`

| # | Claim | Status | Evidence |
|---|---|---|---|
| D1 | "`try` mirrors `ExecuteTryAll`", "`catch`: `ExecuteCatchAll`… once per caught message", and "each stepper mode copies its parent's engine behaviour" | **wrong in one respect: order** | `B81/internal/component/processor/execute.go:70-97` (`ExecuteTryAll`) and `:107-140` (`ExecuteCatchAll`) are **processor-major**: run processor *i* on every message, then processor *i+1*. With the rewrite, `try`/`catch` get one child (the stepper), and they call it once per one-message batch (`processor_try.go:96-104`, `processor_catch.go:78-86`). The stepper then runs **all** children on that message (`engine/stepper.go:140-204`), so the order becomes **message-major**. Content is the same for stateless children. It differs when children share state across messages within one `try`/`catch` (a `cache` set by child 2 and read by child 1, `dedupe`, a rate limit, `log` ordering, or an external side effect). `for_each` and `retry` are already message-major in the engine (`processor_for_each.go:63`, `processor_retry.go:229`), so they're unaffected. `testdata/equivalence/try` and `catch` use only stateless mappings, so AD-8 can't catch this. **Fix:** either add a caveat to AD-7/AD-8 (equivalence holds for children with no cross-message state) plus a corpus case that pins the known difference, or have the stepper reproduce processor-major order |
